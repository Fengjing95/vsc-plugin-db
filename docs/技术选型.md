## 1. 硬约束（不在选择范围内，所有候选必须服从）

| # | 约束 | 说明 |
|---|---|---|
| C-1 | Extension Host **仅支持 CommonJS** | 已核实：ESM 支持的官方 issue（microsoft/vscode#142731 等）至今未落地。产物必须打包为 CJS；源码可以写 ESM/TS，由构建器输出 CJS |
| C-2 | Webview 无 Node、受 CSP 限制 | Webview 是纯浏览器环境；资源本地打包（不走 CDN）；`@vscode/webview-ui-toolkit` 已于 2025-01-01 废弃、仓库归档（已核实），**不能作为组件库候选** |
| C-3 | `engines.vscode ^1.85`（ADR D-11） | 1.85 的 Extension Host 内置 Node 18：`node:sqlite`（需 Node ≥22.5，且 Node 24 中仍为实验态，已核实）在此基线**不可用**。备选：上调 engines 下限（2026 年上调至 ^1.95+ 几乎不损失用户）以解锁 Node 20+——若采纳需同步修订 ADR D-11 |
| C-4 | Native 模块需按 VSCode Electron ABI 编译 | `better-sqlite3` 等 native 依赖存在 ABI 匹配/打包摩擦（vsce 打包 target）；纯 JS / WASM 实现零摩擦 |
| C-5 | 桌面版限定（ADR D-11） | 数据库客户端库选型排除“仅浏览器/WASM-only 且性能不足”的实现 |
| C-6 | 整体许可 Apache-2.0（评审确认） | 引入的依赖许可必须兼容；商用付费库（如 Handsontable）需额外采购 |

## 3. 决策项

### T-01 工程结构（影响：全局；概要 7.1 已按 A 方案设计，此处确认）

| 候选 | 说明 | 优势 | 劣势 |
|---|---|---|---|
| **A. pnpm monorepo 多包** | core / protocol / extension / webview-ui / driver-* 同仓 | 驱动契约同源引用；原子提交；符合驱动规范“单一契约源”要求 | 仓库治理略复杂 |
| B. 单包扩展 | 全部代码一个 package | 最简单 | 驱动可插拔目标（ADR D-07）难以实现 |
| C. 多仓库 | core 与驱动分仓 | 权限隔离清晰 | 契约版本同步成本高，MVP 不必要 |

**推荐：A**（维持概要 7.1 结构）。**决策：☐**

### T-02 扩展端构建工具（影响：M0；概要 7.2 初选：esbuild / tsdown）

| 候选 | 状态（已核实） | 优势 | 劣势/风险 |
|---|---|---|---|
| A. esbuild 直用 | 成熟稳定 | 极快；VSCode 官方脚手架默认路线；资料最多 | 配置代码自己维护 |
| B. tsup | 维护模式（停止新特性） | 与 esbuild 同内核 | 生态正在迁出，不建议新项目 |
| C. tsdown | tsup 官方后继，基于 Rolldown；Rolldown 1.0 stable（2026-05） | 更快、库打包特性全（dts 生成对 monorepo 契约包有价值） | 相对新，边界问题偶发 |
| D. webpack | 传统方案 | 无 | 慢、配置重，不推荐 |

**推荐：A（M0 直接可用）；C 作为可升级路径（dts 生成对 protocol/core 包有价值）。二者切换成本低。**
**决策：☐**

### T-03 Webview 端构建（影响：M0/M3）

| 候选 | 优势 | 劣势 |
|---|---|---|
| **A. Vite** | React/Vue/Svelte 生态标准；HMR 开发体验好；产物本地打包进 webview | 需配置 CSP 兼容输出 |
| B. esbuild 裸用 | 与扩展端统一 | 无 HMR，开发体验差 |

**推荐：A**（Vite 8 已由 Rolldown 驱动，与 T-02 选项 C 同基座）。**决策：☐**

### T-04 包管理与任务编排（影响：M0）

| 候选 | 优势 | 劣势 |
|---|---|---|
| **A. pnpm workspaces**（+ 可选 Turborepo） | 磁盘/安装效率最高；workspace 协议成熟；monorepo 事实标准 | 无 |
| B. npm workspaces | 零额外工具 | 慢，幽灵依赖治理弱 |
| C. yarn berry | PnP 严格 | VSCode 扩展生态兼容性偶有摩擦 |

**推荐：A**。任务编排 M0 不需要（pnpm -r 足够），包数 >8 再评估 Turborepo。**决策：☐**

### T-05 Webview UI 框架（影响：M3；概要 7.2 初选：React）

| 候选 | 优势 | 劣势/风险 |
|---|---|---|
| **A. React 18** | 生态最大；TanStack 系、可视化、AI 组件全兼容；招人/资料容易 | 无明显 |
| B. Vue 3 | 模板开发效率高；国内生态好 | TanStack 有官方适配但社区示例少 |
| C. Svelte 5 | 产物最小 | 组件库适配最薄 |
| D. Preact | 体积小 | 兼容层偶有边角问题，收益（几十 KB）不大 |

**推荐：A**。表格视图是“重交互 + 第三方库密集”场景，React 生态优势明显。**决策：☐**

### T-06 数据网格 ★核心（影响：M3/M4；概要 7.2 初选：TanStack Table + Virtual）

| 候选 | 渲染 | 许可 | 优势 | 劣势/风险 |
|---|---|---|---|---|
| **A. TanStack Table v8 + Virtual v3** | headless + DOM 虚拟滚动 | MIT | 无头可控：单元格渲染/编辑器/值编码展示完全自定；与 ChangeSet 状态层贴合度最高 | 装配工作量自担（列宽拖拽、右键菜单需自行组装） |
| B. AG Grid Community | 完整 DOM | MIT | 排序/筛选/列拖拽/冻结/键盘导航开箱即用 | 体积大（数百 KB）；Excel 导出、行分组等在 Enterprise（付费）；深度定制受 API 边界约束 |
| C. Glide Data Grid | **Canvas** | MIT | 十万行级最流畅、内存小、内置编辑 | 大文本/JSON 查看器等非常规单元格需自建；仅 React；无障碍与中文 IME 需实测 |
| D. Handsontable | DOM | **商用付费** | 类 Excel 交互最全 | 采购成本 + C-6 合规负担 |
| E. RevoGrid | DOM | MIT | 轻量、功能较全 | 社区规模与文档厚度不及 A/B |

**推荐：A**。本项目关键诉求是“单元格内编辑 + 值编码渲染可控 + ChangeSet 集成”，headless 最贴合；性能目标（1000 行×20 列 <1.5s）DOM 方案完全可达成，Canvas 的极致规模非 MVP 必需。若后续普遍面对 5 万行级结果集，可平替评估 C。
**决策：☐**

### T-07 Webview 组件库与样式（影响：M3；Toolkit 已废弃，见 C-2）

| 候选 | 说明 | 优势 | 劣势 |
|---|---|---|---|
| **A. 自建小组件 + `--vscode-*` 主题变量** | button/input/select/modal 约十来个基础件 | 与 VSCode 观感 100% 一致（官方推荐路线）；无依赖 | 组件自维护 |
| B. Radix UI（headless）+ 自适配主题 | 行为无头，样式自定 | 可访问性行为白得（焦点陷阱/ARIA） | 仍需自写样式对齐 VSCode 观感 |
| C. Fluent UI v9 | 微软系组件库 | 组件全 | Office 观感，与 VSCode 风格有差异；体积大 |
| D. Tailwind CSS v4 + 自建 | 原子化样式 | 写样式快 | 与 `--vscode-*` 变量结合需约定 token 层 |

**推荐：A 或 A+D 组合**（自建组件 + Tailwind 做布局/间距，颜色一律走 `--vscode-*` 变量）；B 作为交互复杂（Modal 焦点管理）时引入的增强。交互稿 §11 的无障碍要求不因选型降低。**决策：☐**

### T-08 Webview 状态管理（影响：M3/M4；概要 7.2 初选：Zustand）

| 候选 | 优势 | 劣势 |
|---|---|---|
| **A. Zustand** | 轻量、无 Provider 嵌套；中间件（persist/undo）够用 | 无 |
| B. Jotai | 原子化细粒度 | 表格这种“整表状态”场景不如 store 直白 |
| C. Redux Toolkit | DevTools 强 | 样板代码多，收益低 |

**推荐：A**。注意 ChangeSet 权威副本在 Host（ADR D-06），Webview 状态只是编辑视图，复杂度有限。**决策：☐**

### T-09 Webview ↔ Host 通信（影响：M0/M3；概要 7.4 已定义协议）

| 候选 | 说明 | 评估 |
|---|---|---|
| **A. 自研 RPC + zod** | 按 7.4 帧格式实现（约 200 行） | **推荐**。协议已设计完毕且属核心契约，双端 zod 校验（ADR D-06）天然融入；社区无事实标准库，第三方包用户基数小、风险高于自研 |
| B. 社区 RPC 库 | 现成 | 质量参差、缺乏多端校验与快照恢复语义，需深度改造，不如自研 |

**推荐：A**。**决策：☐**

### T-10 SQL 解析与格式化（影响：M2/M5；概要 7.2 初选：node-sql-parser + sql-formatter）

| 用途 | 候选 | 评估 |
|---|---|---|
| 语句切分 / 危险判定 AST | **A. node-sql-parser**（推荐） | 多方言（MySQL/PG 等）AST，覆盖切分与 DangerGuard 判定；社区大 |
| | B. dt-sql-parser（DTStack，ANTLR） | 方言覆盖更广（含 Hive/Spark/Redis 等，以其文档为准）；体积与上手成本更高，MVP 用不到 |
| | C. pgsql-ast-parser | 仅 PG，不通用 |
| 格式化 | **A. sql-formatter**（推荐） | 方言全、成熟；B. prettier-plugin-sql 依赖 prettier 管线，收益低 |

**推荐：A + A**。dt-sql-parser 列为 P2 备选（若后续要支持大数据方言）。**决策：☐**

### T-11 数据库客户端库（影响：M1/M6；★一项与概要初选不同）

| 数据库 | 候选 | 状态与评估（已核实项已标注） | 推荐 |
|---|---|---|---|
| MySQL | **mysql2** | 事实标准，Promise/预编译/连接池 | ✅ 维持初选，无争议 |
| PostgreSQL | **pg**（node-postgres） | CJS、久经考验、生态默认 | ✅ 推荐 |
| | postgres.js | 更现代的 API，ESM 优先，打包 CJS 需验证 | 备选 |
| Redis | **node-redis**（`redis` 包 v5） | **已核实**：Redis 官方推荐新项目使用；活跃开发 | ✅ **修正初选**（概要 7.2 原写 ioredis） |
| | ioredis | **已核实**：已由 Redis 收购并转维护模式（仅关键修复），Cluster/Sentinel 人体工学仍好 | 短期可用，不建议新项目 |
| SQLite（测试/演示驱动） | better-sqlite3 | 快，但 native → 受 C-4 ABI 约束 | 可用，需处理打包 |
| | sql.js（WASM） | 零 ABI 摩擦、跨平台打包最稳 | ✅ 推荐（CI/e2e 友好） |
| | node:sqlite | 零依赖，但需 Node ≥22.5 且仍为实验态（已核实）→ 受 C-3 约束 | 仅当 engines 上调后评估 |
| SSH 隧道 | **ssh2** | 唯一主流实现 | ✅ 无争议 |

> **需要你注意的分歧点**：Redis 一项，官方生态信号明确指向 node-redis（[redis/ioredis](https://github.com/redis/ioredis) 自述）。ioredis 的优势仅剩 Cluster/Sentinel 配置体验，而我们的驱动规范把连接参数抽象进 FormSchema，可以屏蔽这层差异。建议按 node-redis 修正概要 7.2。
**决策：☐（逐库确认或整体按推荐）**

### T-12 测试框架（影响：M0 起；概要 v0.2 已定 vitest 方向，此处确认）

| 层 | 候选 | 评估 |

| e2e / 集成 | **@vscode/test-electron + @vscode/test-cli** | 官方方案，跑真实 Extension Host；内部断言跑 mocha 风格（test-cli 约定） |

**推荐：A + 官方 e2e**。**决策：☐**

### T-13 代码规范（影响：M0）

| 候选 | 优势 | 劣势 |
|---|---|---|
| **A. ESLint 9（flat config）+ Prettier** | 生态最深（react-hooks、ts-eslint 全套）；团队熟悉度最高 | 双工具两套配置 |

### T-14 CI/CD 与发布（影响：M0 搭建，发布时收口）

| 用途 | 候选 | 推荐 |
|---|---|---|
| CI | GitHub Actions | ✅ 唯一合理项（契约测试仅 Linux runner，见概要 12.5） |
| 打包发布 | **@vscode/vsce**（+ Open VSX `ovsx` 可选） | Marketplace + Open VSX 双发覆盖 VSCodium 用户 |
| 版本/变更管理 | **changesets**（monorepo 多包发版事实标准） | 替代：release-please（单仓更顺，多包弱） |

**推荐：Actions + vsce(+ovsx) + changesets**。**决策：☐**

> **修订（2026-10-10，发布准备批次）**：changesets 部分**按 D-20 修订为「手动 version bump + 手写 CHANGELOG.md」**——仓库唯一发布物是扩展 VSIX（@db-explorer/* 内部包不发 npm），changesets 的多包 npm 发版能力无消费方；CI（Actions）与打包（vsce，`--no-dependencies` + external 闭包物化）按本项落地。修订权威见概要设计 ADR **D-20**（本表不改写历史）。
